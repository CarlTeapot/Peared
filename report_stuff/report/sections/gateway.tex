\subsubsection{გეითვეი (Go სარელეო სერვერი)}

გეითვეი განზრახ „სულელი“ სერვერია (dumb relay): ის დოკუმენტის შესახებ
არაფერს ინახავს, არც სნეფშოტს, არც ოპერაციების ისტორიას, და CRDT
ფრეიმების შიგთავსს არც კი შიფრავს. მისი საქმეა ბაიტების სწრაფად და
სამართლიანად გადაგზავნა. ეს გადაწყვეტილება პირდაპირ გამომდინარეობს
პროექტის ფილოსოფიიდან: სიმართლის წყარო მონაწილეების (და პირველ რიგში
ჰოსტის) რეპლიკებია და სერვერს დოკუმენტზე წვდომა არ სჭირდება.

მისი ძირითადი ცნებებია:
\begin{itemize}[itemsep=0pt]
  \item \textbf{Hub}, ოთახების რეესტრი: ქმნის ოთახებს (\texttt{POST
        /rooms}), პოულობს მათ იდენტიფიკატორით და შლის სესიის ბოლოს;
  \item \textbf{Room}, ერთი სესიის სივრცე: წევრების სია და გადაგზავნის
        ლოგიკა. მიღებული ფრეიმი ეგზავნება ოთახის ყველა წევრს გამგზავნის
        გარდა;
  \item \textbf{Client}, ერთი WebSocket შეერთება: როლი (პირველი
        შემოერთებული ჰოსტია), ჩაწერის უფლების ატომური დროშა და გამავალი
        ფრეიმების ბუფერი.
\end{itemize}

მიუხედავად „სისულელისა“, გეითვეის რამდენიმე აქტიური მოვალეობა მაინც
აქვს. ახალი წევრის შემოსვლისას ის ჰოსტს სნეფშოტის მოთხოვნის საკონტროლო
ფრეიმს უგზავნის და ჰოსტის პასუხს მხოლოდ ახალ წევრს გადასცემს, ასე
გვიან შემოსული სტუმარი წამებში იღებს დოკუმენტის მიმდინარე მდგომარეობას,
ისე, რომ სერვერს დოკუმენტის შენახვა არ დასჭირვებია. წევრის ყოველ
შემოსვლა-გასვლაზე ოთახი ყველას უგზავნის წევრობის ფრეიმს (ამას ნაგვის
შემგროვებელი იყენებს) და ახალ წევრს, არსებული წევრების სრულ სიას
სახელებითა და უფლებებით. უფლებების ფრეიმებზე ის ავტორიტეტულ არბიტრს
თამაშობს: მოთხოვნას მხოლოდ ჰოსტისგან იღებს, ჰოსტის საკუთარი უფლების
შეცვლას კრძალავს, ხოლო წაკითხვის რეჟიმში მყოფი წევრის ოპერაციებს
ჩუმად აგდებს.

უსაფრთხოებისა და მდგრადობის მხრივ: ყველა HTTP ენდპოინტი (გარდა
\texttt{/health} და \texttt{/ws}) მოითხოვს bearer ტოკენს, რომელიც მხოლოდ
ჰოსტის აპლიკაციამ იცის; WebSocket შეერთებების სიხშირე შეზღუდულია
(ნაგულისხმევად 5 შეერთება წუთში ერთი მისამართიდან, კონფიგურირებადი);
ხოლო თუ რომელიმე კლიენტი ფრეიმებს ვერ ასწრებს მიღებას (ნელი ქსელი,
გაჭედილი პროცესი), მისი ბუფერი ივსება და გეითვეი მას გათიშავს, რომ
დანარჩენი ოთახი არ შეაფერხოს, ეს ე.წ. slow client problem-ის
სტანდარტული გადაწყვეტაა. ამას ემატება ზემოთ ნახსენები მეტრიკების
რეესტრი, რომელსაც ჰოსტის აპლიკაცია პერიოდულად კითხულობს.

გეითვეი მთლიანად უმდგომარეო (stateless) და ერთსესიიანია: ის ჰოსტის
აპლიკაციასთან ერთად იბადება, ერთ ოთახს ემსახურება და სესიის
დასრულებისას (\texttt{POST /end-session} ან ჰოსტის ფანჯრის დახურვისას)
წევრებს სესიის დასრულების ფრეიმს უგზავნის და ითიშება. Go ამ ამოცანას
ბუნებრივად მოერგო: goroutine-ები და არხები ზუსტად ის პრიმიტივებია, რაც
„თითო კლიენტზე ორი მარყუჟი, ოთახზე ერთი გამანაწილებელი“ ტიპის
არქიტექტურას სჭირდება, ხოლო ერთი სტატიკური ბინარი sidecar-ად
გასაშვებად იდეალურია.
